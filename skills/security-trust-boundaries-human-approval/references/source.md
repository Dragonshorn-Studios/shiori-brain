# Security, Trust Boundaries & Human Approval

Cross-project rules for agents, automation, CI workers and MCP applications.

## Classify every boundary

Before implementation, identify:
- trusted orchestrator and operator;
- untrusted repository content, user input, webhook payloads, model output and subprocess output;
- credentials and secret references;
- external systems that can be read or mutated;
- irreversible or expensive operations.

## Least authority
- Grant the smallest filesystem, network, GitHub App, database and process permissions required.
- Keep external publication in a trusted component.
- Workers that analyze code must not automatically gain the ability to publish, merge or deploy.
- Prefer short-lived credentials and references resolved at execution time.

## Fail closed

Reject malformed, ambiguous, unauthorized or out-of-scope requests. Do not guess a target, silently downgrade a validation failure or continue after losing the evidence needed to act safely.

## Human approval

Use a propose → inspect → approve → execute flow for consequential mutations such as deployment, secret changes, destructive maintenance, external publication or broad automated fixes. Approval must bind to the exact proposed action and revision.

## Secret handling
- Never commit `.env`, tokens, cookies, private keys or credential-bearing URLs.
- Never echo secrets in logs, errors, screenshots, artifacts or model prompts.
- Redact before persistence and before crossing process boundaries.
- Store only what is necessary and encrypt sensitive values at rest.

## Isolation and reproducibility
- Run untrusted code in an isolated workspace with bounded time and resources.
- Pin the exact revision under review.
- Make retries idempotent.
- Preserve an audit trail of proposals, approvals, execution result and actor.
- Treat generated content as data until it passes validation.
